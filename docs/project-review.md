# A bounded decision → implementation → result → review loop

This is a small continuity experiment, not a project-management framework. The existing Council engine still makes one bounded decision. An external coordinator (for example Build With Me, when installed) owns the project and explicitly decides when another Council run is warranted. Codex/Claude or another executor builds only within the owner's actual permission.

The clone's baseline branch `baseline/council-main` has exactly the file tree of `Roronoa-code/council` at `af5d94a16decad673b056d9156dabdedbec37f5f`. Its Git history and repository settings are not a mirror of upstream. The patch is isolated from the original repository.

## What changed, and what did not

`handoff.md` now retains the original constraints, decisive rationale, acceptance criteria, do-not list, full bounded experiment, stop conditions, revisit triggers, uncertainty, dissent and run-qualified evidence references. Demo and single-agent notices remain explicit. Full evidence excerpts stay in the original private report rather than being copied into every handoff.

`report.json` gains an additive `handoff_contract` object. It contains a versioned reference, run/protocol/profile/depth metadata, and canonical SHA-256 hashes of the complete decision and brief. Criterion names AC1, AC2, etc. are scoped to that exact reference. Changing an evidence excerpt, constraint, threshold, criterion or dissent changes the reference. Reordering JSON object keys, updating runtime bookkeeping or resuming an unchanged completed run does not.

There are no new model stages, prompts, dependencies, worker privileges, project commands, persistent database, scheduler, autonomous next-task selection or API billing. Decision schemas and existing checkpoints are unchanged. Engine-generated handoffs have this binding; manually written native-skill answers do not acquire an enforced hash/review process automatically.

## Keep one owner of project state

Reuse a short PROJECT.md for objectives and binding constraints, and STATE.md for the active decision/result references and the next unresolved condition. If these already exist in the coordinator, do not create Council-owned copies. Keep Git/CI/issue-tracker facts in those tools and reference them.

A decision can record `reviews`, `depends on` or `supersedes` in the coordinator's existing log. No general graph engine is required. State the condition in a dependency, not merely another decision's ID. Replacing a strategy must preserve its previous results and costs. An upstream change flags affected work for review; it does not automatically cancel every downstream task.

## 1. Obtain one bounded decision

Use the existing `council run` interface with selected project constraints and evidence. Before implementation, the owner/coordinator reviews the proposal and separately records actual authorization against the exact contract reference and the target repository/base revision. A verdict of proceed or test is not that authorization. A missing or conflicting ceiling is not permission to spend.

For a no-model smoke check from an installed clone environment:

```sh
python -m council demo --out demo-decision
python -m council resume demo-decision
```

Inspect `demo-decision/handoff.md` and `report.json`. The unchanged resume should retain the reference and call count. This is the existing synthetic laundry fixture, not a procurement assessment, live model review or validation of the governance idea. Do not record it as a real economic outcome.

## 2. Execute externally; return a receipt

Copy [the result template](../examples/result-template.md) into the private project as RESULT.md, or add its binding/evidence fields to the coordinator's existing result format. Use one row per actual acceptance criterion; do not invent ACs to make the receipt look complete. Keep the returned receipt outside files regenerated by Council. The renderer never creates or overwrites RESULT.md.

Record the approved reference, separate owner authorization, target base/result revisions, criterion-level evidence, deviations, tests not run, actual observations, costs and human effort. Preserve an uncommitted diff/artifact reference when a commit is unavailable. Differentiate executor claims from independently reproduced checks.

Keep three findings separate:

| Dimension | Review question |
|---|---|
| Approved intent and authority | Was this work actually approved, against this version and these constraints? |
| Actual implementation | What does the diff, test output or independently inspected artifact establish? |
| Actual result | Did observations support the original hypothesis after costs? |

A passing test suite does not demonstrate demand. A failed business experiment does not necessarily mean the code is wrong. New requirements should be proposed as a revision, not silently added to the old acceptance criteria.

## 3. Check binding before another deliberation

The owner/coordinator compares the receipt's reference with the separately retained approved reference. A mismatch, missing approval, missing evidence or unexplained deviation is an exception to resolve, not a pass. The following local check demonstrates recomputation from a completed state; use the Python interpreter of the clone installation:

```python
from pathlib import Path
from council.report import handoff_identity
from council.store import Store

state = Store(Path("demo-decision")).load()
print(handoff_identity(state)["reference"])
```

The algorithm uses the existing canonical JSON digest: sorted object keys, UTF-8, no insignificant separators. `brief_sha256` hashes the full brief; `decision_sha256` hashes the full chair decision. Hash all `handoff_contract` fields except `reference` to obtain its final digest; the reference is `<run_id>:handoff-v1:<digest>`.

This is a deterministic fingerprint, NOT an approval signature or tamper-proof authority boundary. An executor that can replace every source and the owner's approved reference can forge a consistent story. Retain the actual approval outside its write scope. Do not trust a hand-edited Markdown header instead of recomputing from the retained decision/brief. The existing `council validate` command validates decisions, not RESULT.md; this patch does not add a receipt parser or automatic approval enforcement.

## 4. Construct a small review packet and use another ordinary run

Use a new review only at a planned outcome checkpoint or because material evidence/constraints changed. Do not review every file edit, re-open a decision merely because another model disagrees, or automatically call Council from its own worker.

The coordinator selects the current binding constraints, the originating decision/reference, relevant new results, unresolved decision-changing dissent and a few independently inspected evidence excerpts. It must inspect referenced repository files/logs before representing them as verified. Council's restricted workers do not fetch arbitrary URLs or inspect a repository merely because a path appears in a receipt.

A review question can be:

> Review contract <reference> using the attached result receipt. Separately assess conformance to approved intent, actual implementation evidence, and the observed experiment result. Identify missing or contradictory evidence and any triggered stop condition. Preserve the old criteria and unresolved dissent. Recommend one bounded continue/revise/stop/defer action, or waiting when no new action is justified. Do not grant execution or spending permission.

Save that question as `review-question.txt`. Put selected, permissioned source excerpts into `review-evidence.json`, using the existing evidence schema. Keep the contract and receipt compact; for larger files use actual selected line ranges (`FILE::FIRST:LAST`). All binding constraints and material dissent must remain represented. For example, once those local files exist:

```sh
python -m council run --question-file review-question.txt --profile mixed --depth standard --max-calls 5 --retries 0 --mode product --constraint "Read-only review; no execution or spending permission" --context PROJECT.md --context handoff-for-review.md --context RESULT.md --evidence review-evidence.json --out review-001
```

This command IS a live subscription-backed review; it is not run by the demonstration or by CI. Standard depth uses five invocations with no retries in this example, not a token/currency guarantee. No missing provider should become a fallback to API billing. The owner must explicitly choose to run it.

When assembling `handoff-for-review.md`, retain the contract reference and describe any omitted sections; a selected excerpt is not a replacement for the immutable full contract. The existing intake limits remain in force (including 20 evidence records and the 48 KB brief ceiling); choose relevant excerpts rather than relaxing limits or silently truncating them. Evidence IDs such as E1 are local to a brief. Give each selected source a fresh local ID while retaining the original `<run_id>/E1` provenance in its source/description. Selected context files also become evidence records; do not exceed the shared count.

New evidence produces a NEW run linked in STATE.md. Do not edit an old state.json and attempt to resume it. Summaries are derived navigation aids, not authoritative replacements for the original decisions and artifacts. No vector store or whole-history prompt is necessary for this first test.

## Worked Economic Agent sequence — a procedure, not an observed outcome

1. **Opportunity decision:** compare a manual procurement sample with an accessible paid software task and doing nothing. Procurement is conditional on a reachable potential buyer; existing coding subscriptions do not prove demand. First approve only the cheapest observation that can change the choice.
2. **Build decision:** if customer evidence warrants implementation, freeze one customer profile, a saved notice sample, source-linked qualification output, unknown handling and a review-effort metric. Exclude dashboards, automated outreach, purchases and trading. Record actual owner-approved resource limits, not unused hypothetical capital.
3. **External implementation:** Codex returns criterion evidence, target revisions and material deviations. Routine implementation details stay with the executor; no Council call per file.
4. **Outcome review:** separate ingestion of 100 notices from qualification accuracy and prospect willingness to pay. Record sampling, excluded notices, failures, feedback, settled receipts and acquisition/review effort. Processing 100 records does not establish a market.
5. **Next commitment:** accurate output without buyers challenges demand; paying customers with excessive review effort challenge delivery economics. One paid pilot does not authorize scaling. A changed segment/price is a new hypothesis retaining the old costs and failures. Do not extend a stopping rule after disappointing results without an explicit new decision.
6. **Separate trading research:** a later, separately approved read-only/paper experiment has its own frozen baseline, cost model and falsifier. Failed procurement is not automatic permission to start trading; a favourable paper result is not permission for live funds.

The numbers above describe an illustrative review target, not completed work or statistical proof. No prospect contact, payment or live trade is performed by this feature.

## Falsify the need for more architecture

Compare the existing coordinator plus manual handoffs against this version-bound handoff on one real cycle and held-out cases: scope expansion, shifted success criteria, correct implementation with failed economics, and clean work that should not be escalated. Keep evidence access and Council depth comparable. Record consequential discrepancies caught, false alarms, reconstruction time, owner effort and actual model usage.

Start with at most a planned review before commitment and one after meaningful results, plus a genuinely material exception. Waiting/no justified action is valid. If a complete manual handoff achieves the same result at no greater effort, stop here. Automate only a repeatedly observed linking/context-assembly failure. Offline tests verify engineering, not better decisions or a defensible product niche.
